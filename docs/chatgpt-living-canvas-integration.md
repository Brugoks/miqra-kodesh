# ChatGPT ↔ Miqra Qodesh Living Canvas

Implemented locally; **nothing in this change deploys, changes a production schema, registers a live OAuth client, or publishes the sample**. Production changes require the owner's explicit approval.

## Architecture and existing data

ChatGPT → OAuth 2.1 / PKCE with **Supabase Auth as the authorization server** → authenticated Streamable HTTP MCP Edge Function → caller-scoped Supabase client → existing `study_canvases` RLS → React Living Canvas workspace.

This is a custom application integration. Connecting ChatGPT's GitHub or Supabase management plugins does **not** expose these tools.

The existing architecture is preserved:

- `study_canvases.user_id` owns the record. Its owner-only RLS remains unchanged. Organization is context, assigned by the existing `set_organization_id` trigger; changing active organization never transfers access. Organization leaders/admins cannot read someone else's personal canvas. There is no new organization-wide collaboration permission.
- Legacy Scripture studies use up to four `passages`, branching `steps`, notes, and `pins`. `normalizeCanvas` still upgrades old single-workspace/single-explanation records. Integration reads these and supports title changes; it refuses to convert them implicitly.
- Spatial canvases use `journey.kind = 'moment'`, up to 100 entries, and the existing version-1 board. Nodes reference entries; text is not duplicated in nodes. Existing geometry and validators place new cards in free grid slots and preserve existing positions.
- The four-passage legacy limit does not constrain spatial Scripture entries. The sample has eight complete verified passages.
- `step_count` remains generated by PostgreSQL. The integration never writes it, ownership columns, legacy sharing fields, or created/updated timestamps.
- `/study-canvas/shared/:token` and `get_shared_study_canvas` still require a signed-in reader. The database rule forbidding personal journeys from using legacy share tokens remains intact.

New storage:

| Storage | Purpose | Access |
| --- | --- | --- |
| `living_canvas_receipts` | User-scoped retry key, argument hash, small acknowledgement | Owner only; no anonymous grants |
| `living_canvas_publications` | Frozen allowlisted snapshot and random UUID bearer-link token | Owner only; anonymous access solely through token lookup RPC |
| `canvas_integration_private.rate_windows` | Shared per-user request counter | No client table access |
| `canvas_integration_private.oauth_clients` | Administrator-managed OAuth client/resource allowlist for the token hook | Auth hook reader only; never user editable |

`commit_living_canvas_change` runs as **security invoker**, so existing owner RLS authorizes row locks and writes. The transaction takes a user/retry-key advisory lock, checks receipts, locks the canvas, compares `updated_at`, performs a whitelisted write, and inserts the receipt. Concurrent retries cannot create two canvases. Concurrent browser autosaves cause a conflict instead of losing changes.

## Current supported ChatGPT mechanism

Use a **custom MCP server/plugin**, with stateless Streamable HTTP and OAuth 2.1, rather than the retired plugin manifest approach. This implementation supports the MCP `initialize`, `notifications/initialized`, `ping`, `tools/list`, and `tools/call` methods and negotiates protocol versions 2025-03-26, 2025-06-18, and 2025-11-25. It uses JSON HTTP responses, not a persistent SSE subscription. Batches, session persistence and server-initiated messages are unsupported.

## Authentication setup

Perform these steps in a **separate staging Supabase project first**. Do not use production for acceptance tests.

1. Apply the existing app schema and the new migration `20261031181822_chatgpt_living_canvas_integration.sql` to staging through the repository's normal reviewed migration process. The repository currently has no `supabase/config.toml`; configure/link a separate staging CLI workspace explicitly. Do not run a blanket database push against the production-linked project.
2. Deploy the frontend to staging so `/oauth/consent` and `/study-canvas/published/:token` exist. The consent route preserves the authorization query while the existing app sign-in wall authenticates the user, including a same-origin return URL for provider sign-in, then displays the Supabase-verified client and identity permissions. Add the staging `/oauth/consent` and `/study-canvas` return URLs to Supabase Auth's ordinary sign-in redirect allowlist as well as setting the OAuth server authorization path. Connection never automatically publishes anything.
3. In Supabase **Authentication → OAuth Server**, enable the OAuth 2.1 server and set its authorization path to `/oauth/consent` on that frontend's configured site URL. Use an asymmetric JWT signing key as required for OIDC. Supabase handles PKCE, authorization codes, exact callback validation and refresh rotation.
4. Create a dedicated OAuth client for the staging ChatGPT connection. Use a predefined client with the token endpoint authentication method supported by the ChatGPT connection form and Supabase (`none` for a public PKCE client, or `client_secret_basic` / `client_secret_post` for a confidential client). Keep dynamic registration disabled for this deployment: unknown client IDs intentionally fail closed.
5. Copy the **exact callback URI shown by ChatGPT's MCP connection setup/management page** into the Supabase OAuth client's redirect allowlist. Do not guess a callback ID or use wildcard URLs. OpenAI's current documented callback can be connection-specific (`https://chatgpt.com/connector/oauth/{callback_id}`) or the stable callback when issuer-identification requirements are met; use the one actually shown for this connection. If needed, create the connection draft first to obtain its callback, then complete its OAuth credentials.
6. In the staging SQL editor, configure the trusted client/resource binding. These are identifiers, not secrets:

   ```sql
   insert into canvas_integration_private.oauth_clients (client_id, resource)
   values ('YOUR_REGISTERED_OAUTH_CLIENT_ID', 'https://YOUR_PROJECT.supabase.co/functions/v1/living-canvas-api/mcp');
   ```

7. In **Authentication → Hooks**, enable `public.living_canvas_access_token_hook` as the Custom Access Token hook. If a hook already exists, compose this logic into it instead of replacing existing claims. The hook sets `canvas_integration: true` and audience `['authenticated', '<exact MCP resource>']` only for an administrator-allowlisted client. Other app sessions remain unchanged. Keeping `authenticated` preserves Supabase's own API audience validation.
8. Set the Edge Function environment values below. The client IDs must match both the registered OAuth client and the database allowlist.
9. Deploy only this function, with gateway JWT verification disabled so unauthenticated OAuth discovery can reach the handler. **The handler itself still verifies every tool request.** Example command, to run only after deployment approval:

   ```sh
   supabase functions deploy living-canvas-api --project-ref YOUR_STAGING_PROJECT_REF --no-verify-jwt
   ```

10. Inspect the Supabase discovery document and confirm its issuer is exactly `https://YOUR_PROJECT.supabase.co/auth/v1`, with authorization-code PKCE/S256 and the chosen client authentication method:

    `https://YOUR_PROJECT.supabase.co/.well-known/oauth-authorization-server/auth/v1`

11. Test with MCP Inspector and a staging user before connecting ChatGPT. Confirm regular browser access tokens, expired tokens, unregistered clients, and tokens without the MCP audience fail with 401. Then test real OAuth consent, refresh, denial and reconnection. Those hosted OAuth steps require staged deployment and have **not** been exercised by the local fixtures.

## Endpoints and schemas

Let `BASE = https://YOUR_PROJECT.supabase.co/functions/v1/living-canvas-api`.

| Endpoint | Method | Authentication |
| --- | --- | --- |
| `BASE/mcp` | POST JSON-RPC | OAuth bearer token |
| `BASE/.well-known/oauth-protected-resource` | GET | Public discovery only |
| `BASE/tools/<tool_name>` | POST JSON arguments | Same OAuth bearer token and validation as MCP |
| Frontend `/oauth/consent?authorization_id=...` | Browser | Existing account sign-in |
| Frontend `/study-canvas?canvas=<id>` | Browser | Existing owner sign-in |
| Frontend `/study-canvas/published/<token>` | Browser | Anonymous read-only snapshot |

The MCP 401 `WWW-Authenticate` challenge explicitly advertises the metadata URL, including its function path. No root-domain rewrite is necessary.

Authoritative machine-readable input/output schemas are exported as `TOOLS` in `supabase/functions/living-canvas-api/tools.js` and returned by `tools/list`. The same input registry validates every REST/MCP call, including unknown-field rejection. IDs are UUIDs for canvases and existing board/entry IDs for content. All writes require a user-unique `idempotency_key` (8–128 characters). Every existing-canvas write requires the exact `expected_updated_at` returned by `get_canvas` or the preceding mutation.

| Tool | Required arguments beyond retry/revision fields | Optional arguments | Result inside `result` |
| --- | --- | --- | --- |
| `create_canvas` | `title`, `moment` (central question) | `insights` (max 40), `scriptures` (max 12) | `canvas_id`, `updated_at`, `canvas_url` |
| `get_canvas` | `canvas_id` | — | Normalized `canvas`, `updated_at` |
| `update_canvas` | `canvas_id`, `expected_updated_at` | `title`, `entries: [{id,text}]`, `placements: [{node_id,x,y}]`, `sections: [{id,title,entry_ids,color?}]` | Mutation acknowledgement |
| `add_scripture` | `canvas_id`, revision, `reference` | `translation` (`BSB` default or `KJV`), contextual `note` | Mutation acknowledgement |
| `add_insight` | `canvas_id`, revision, `category`, `text` | `source_entry_ids`, `evidence_urls` | Mutation acknowledgement |
| `connect_concepts` | `canvas_id`, revision, existing `source`, `target`, `label` | `direction` (`forward` default or `none`) | Mutation acknowledgement |
| `publish_canvas` | `canvas_id`, revision, `explicit_public_authorization: true`, selected `entry_ids` | `revoke: true` disables the link and does not require entry IDs | Acknowledgement plus `published_url`, `token`, `published_at`; or `revoked: true` |
| `list_canvases` | None | `limit` (1–50, default 20), `offset` (0–10000) | `canvases` summaries, `next_offset` or null |

Get the canvas after creation/addition to discover server-created entry/node IDs. Existing-node positions persist; sections group existing cards without automatically moving them. Use explicit placements when reorganizing. Both source and target must exist, differ, and have no existing connection in either direction. One canonical entry per attached reference/translation prevents accidental duplicate passages.

REST results and MCP `structuredContent` share the envelope `{ "result": { ... } }`. MCP also returns the same JSON as text content. It marks read tools read-only, writes idempotent, and publishing destructive to prompt host review. Annotations are hints; actual authorization, revisions and filtering are enforced server-side.

Example private creation:

```json
{
  "idempotency_key": "wisdom-discussion-001",
  "title": "Wisdom Without Control",
  "moment": "How can we equip others without determining their conclusions?",
  "scriptures": [{"reference": "Exodus 18:13–26", "translation": "KJV"}],
  "insights": [{"category": "application", "text": "Draw Out → Reframe → Examine Scripture → Wrestle → Refine. This is a proposed study heuristic."}]
}
```

Use a fresh key for a new intention. Retry a timed-out write with the **same key and arguments**. Reusing a key with different arguments returns `idempotency_conflict`. A replay returns the original acknowledgement, even if later edits exist; retrieve the canvas before continuing. Receipts are retained until account deletion unless an administrator introduces an explicit retention policy. Do not purge them without defining a new retry horizon.

## Scripture-aware content

Categories: `scripture`, `historical_context`, `observation`, `interpretation`, `application`, `counterargument`, `reflection`, `open_question`.

The existing journey kinds remain unchanged: categories are preserved metadata on existing reflection/response/question/Scripture entries. Labels render on board cards and in the outline. AI-assisted provenance is shown beside full card content and retained on edits/exports. Every insight remains editable through the real workspace.

`add_scripture` and `create_canvas.scriptures` accept references and translation identifiers, **never quotations**. They reuse the existing one-chapter reference parser and HelloAO verse-content flattener, fetch BSB or `eng_kjv`, reject missing verses, and save a frozen `biblePassage` separately from the editable contextual note. The frontend editor keeps the verified passage/reference attached. A provider failure fails the request rather than inventing text. Multi-chapter ranges require separate additions.

Historical context requires HTTPS evidence URLs. The integration labels those URLs **unverified**; it does not fact-check a model's historical or theological claims. Source-entry references must name existing entries. Models/users must still evaluate claims against evidence and Scripture; no application or heuristic is treated as biblical text.

## Publishing policy

Private is always the default. `publish_canvas` is an explicit public disclosure action, not an autosave option.

- Ask for authorization for the exact selected cards at a retrieved revision. Passing `explicit_public_authorization: true` records the caller's assertion of that authorization; the server cannot independently prove a natural-language conversation's intent. Host confirmation annotations complement this assertion.
- SQL reconstructs the projection from stored entries, **not from a caller-supplied snapshot**. Prayers, personal reflections and uncategorized journal entries are rejected even when selected. There is no switch to publish these personal categories.
- The public snapshot includes the deliberately published **title**, selected card text, translation/passages, connecting labels between selected cards, and filtered geometry. Original glimpse, notes, sermon-source metadata, revisit dates, owner/account/org details and private section titles are omitted. Section names become neutral `Theme N` labels.
- Review selected card text, title and connecting labels for information you do not intend to disclose. A personal statement deliberately written inside an observation/application is still selected content; no semantic privacy classifier is claimed.
- Anyone possessing the random link may view and pan/zoom the read-only board and open its full cards without signing in. Anonymous clients cannot select publication tables, update canvases or call mutations.
- Subsequent private changes are invisible until a separately authorized republish. Republish replaces the snapshot behind the same link; revoke deletes it. Publishing after revoke creates a new token. Old retry keys may acknowledge an old/revoked link, so use a fresh key for a new publication.
- Revoke with `publish_canvas` plus `revoke: true`, a fresh retry key, a current revision and explicit authorization. Owner deletion cascades publication deletion. As with all public sharing, revocation does not erase copies already saved by readers.

## Security model

- The Edge Function uses only the public project key and **the caller's verified JWT**. No service-role client is constructed. `getClaims` verifies the token; the handler checks exact issuer, expiration, resource audience, authenticated role, nonanonymous identity, approved `client_id` and trusted integration claim. `getUser` additionally checks the current account and matching subject.
- Supabase OAuth OIDC scopes describe identity information; they are not database permission scopes. This connection uses the user's existing RLS permissions and is trusted to read their private canvases. It is **not** a sandbox for an untrusted OAuth application or a replacement for auditing the project's other existing APIs/RPC grants. No organization admin bypass is added.
- The allowlist/token hook uses administrator-controlled storage, never editable user metadata. Ordinary browser tokens fail the MCP audience/client checks. Database owner RLS remains the final row authorization boundary.
- A maximum 256 KiB JSON body is enforced while streaming, regardless of `Content-Length`. Inputs reject ownership and sharing overrides, unknown keys, invalid IDs, unbounded positions, board versions, dangling/duplicate connections and unsupported categories.
- A database-backed fixed window allows 60 authenticated requests per user/minute across Edge isolates, including retries and protocol calls. Rate counter tables are not writable by clients. Responses include 429 and `Retry-After: 60`. The anonymous published-token RPC uses an unguessable token; edge/CDN abuse protection remains a hosting concern.
- Retry receipts and row locks are transactional. Existing-canvas writes require exact revisions and never perform fallback upserts. Service errors expose concise messages, not stacks, SQL or secrets.
- Stored content is treated as data, not tool instructions. The React renderer uses escaped text; no HTML injection or arbitrary URL fetching from content is introduced. The API does not run a model or follow instructions embedded in saved canvases.
- Authenticated responses use `Cache-Control: no-store`. The MCP resource rejects unexpected browser Origins and uses no cookie authentication or permissive CORS. Public viewing uses the existing Supabase RPC client.
- The public token reader and protected rate-counter function are narrowly scoped security-definer functions with empty search paths, explicit grants, and no arbitrary user ID argument. Canvas writes use security invoker.
- Disconnect the plugin and revoke its Supabase OAuth grant to stop refresh. Existing access JWTs can remain valid until expiry; use a short token lifetime. To disable a client immediately at this endpoint, remove it from `LIVING_CANVAS_OAUTH_CLIENT_IDS` and reload the function configuration; remove its hook allowlist entry to prevent new integration-marked tokens.

## Errors and troubleshooting

REST errors use `{ "error": { "code": "...", "message": "..." } }`. MCP tool failures return HTTP 200 with `isError: true` and the same model-readable error object in text content. Authentication/transport failures retain their HTTP status.

| Error/status | Action |
| --- | --- |
| 401 `authentication_required` | Connect/reconnect OAuth; check hook, approved client ID, exact issuer and audience; ordinary app JWTs intentionally fail |
| 403 `forbidden` | Check owner RLS and registered user's access; organization context is not permission |
| 404 `not_found` | Wrong/deleted canvas or someone else's canvas; these are deliberately indistinguishable |
| 409 `revision_conflict` | Retrieve again, review intervening changes, reapply intent with current revision and a fresh key |
| 409 `idempotency_conflict` | Same key used for another request; reuse identical args for a retry or choose a fresh key for a new intention |
| 413 `request_too_large` | Split into smaller additions; limit is 256 KiB UTF-8 bytes |
| 429 `rate_limited` | Wait for the shared minute window; honor `Retry-After` |
| 502 `scripture_unavailable` | Retry later; no generated fallback Bible text is used |
| 503 `storage_unavailable` | Check staging migrations/grants; retry the identical request/key |
| Metadata URL returns gateway 401 | Deploy this function with `--no-verify-jwt`; keep in-handler token validation enabled |
| Shared/public page seems empty | Distinguish legacy signed-in `/shared/` links from snapshot `/published/` links; check token and publication revocation |
| Board cannot be safely edited | Unsupported/damaged board; open/export in the app; never overwrite an unreadable layout |

For staging diagnostics, inspect function logs without recording Authorization headers or private bodies, run Supabase security advisors against **staging**, and verify all new public tables have RLS. If an existing token hook is used, test its composed claims for both ordinary app sessions and the registered OAuth client.

The CLI's security-advisor run against the temporary PostgreSQL fixture could not complete because it required TLS; the fixture intentionally uses a local Unix socket. Local SQL checks separately verify every new table's RLS, sensitive RPC grants, owner isolation, and invoker rights. Hosted Supabase advisors remain part of staging verification.
